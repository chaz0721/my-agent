## 5. SPI 漏洞
1. **扩展拿不到父的 provider**（ModelSummarizerImpl 也是由 cli 传入 Supplier）。已由 `subLoop` 和 `Settings.withProvider` 解决。
2. **扩展拿不到 hooks 链**，所以子代理无法"审批照常走父的 UI"。已由 `subLoop` 解决：只转发 before/after。
3. **扩展无法列出工具**，只有 `tool(name)`。已由 `subLoop` 的 `offered` 解决：由宿主在注册表上过滤。
4. 新发现：**子代理里调用会写 session entry 的工具，entry 会落进父 session**。`ctx.appendEntry` 绑定的是宿主当前的 session，`todo_write` 就是这种情况，而且调用发生在子代理线程上，会和父 loop 竞争 leaf。我按名字排除了 `todo_write`/`todo_read`（见 §6-3）。通用的修法要么是让工具自描述"绑定父 session"，要么是让 `subLoop` 给子代理换一个 SessionAccess。现在没有这样的 SPI，第三方扩展的同类工具仍会出这个问题。

## 6. 偏离与理由
1. **写冲突锁不是"每路径一个 `ReentrantLock`"**，而是用一个 `ReentrantLock` 加 `Condition` 保护 `path → (owner, count)` 表，owner 是子代理 run（父代理是一个固定对象），并且对 owner 可重入。原因是：锁在 beforeToolCall 里取，这一步在 loop 线程上；而 afterToolCall 在并行模式下跑在 worker 线程上。线程绑定的 ReentrantLock 在另一个线程上 unlock 会抛 IllegalMonitorStateException。释放按 ToolCall 对象身份（IdentityHashMap）进行，不同 run 的 call id 相同也不会串。另外两点：锁同样作用于父代理的写，父代理的写不会和后台子代理撞；等待时 notify 一行，等待中按 200ms 检查一次取消。
2. **子代理自己的压缩要用 `ModelSummarizerImpl`，但它需要 `Supplier<Provider>`。** 扩展手里没有 provider，所以新增了 `LoopProviderImpl`：每个摘要请求跑一个单 turn、无工具的 `subLoop`。这样复用了 core 的摘要提示词和校验，没有复制一份。两段 stage 用 `Compaction(…, sideStore, Target(sideId)).stages()`，`withLeaf` 指向侧链的 leaf。
3. **general 类型也拿不到 `todo_write`/`todo_read`**，理由见 §5-4。规格原话是"父的全部工具（除 spawn_agent）"。
4. foreground 的 `spawn_agent` 也在独立的 `pai-subagent-<runId>` 平台线程上跑：调用线程以 100ms 一次轮询 progress 队列，再交给 `tc.progress`，这样 ToolRunner 的 sink 只在调用线程上被调用，线程名也统一。后台 run 完成时会 notify 一行。
5. 未完成的 `subagent` entry 不会从子代理线程直接写入。它们先进队列，由父 loop 线程或工具线程在这三个时点写入：`prepareRequest`、foreground 结束、`agent_result`；`SessionEnded` 和 `onUnload` 时会 join（最多 10s）后再写。原因是 Repl 的 leaf 字段不是线程安全的。

## 7. 坑
- 外层 shell 会吞掉 `-Command` 里的 `$变量`，所以凡是用到变量的命令都写成 `.ps1`。`D:\PaiCLI\tmp\m75live\verify.ps1`、`pull.ps1`、`run.ps1`、`cancel.ps1` 都可以复用。同步方式：容器里把变更文件 tar 到唯一 outputs 路径（`scratchpad/push.sh`），电脑上先核对 MD5，再 `tar -xf` 并跑 `spotless:apply verify`；回程用 `git diff --binary 1112ac3 HEAD` 生成 patch，在容器里 `git apply`。
- 只读 bash 的规则会让 explore 里带引号的 `rg -n "x" .` 一律被拦（M7 P0 的设计）。DeepSeek 会改用 `ls` 和 `read`，但多花几轮。`git ls-files` 也被拦，因为它不在只读表里。
- Plain renderer 下 `notify` 走 stdout，子代理的 `waits` 和 `finished` 提示会插在父代理输出的中间（`lock.log` 165 行）。
- Ctrl+C 的 live 复现：stdin 的最后一行如果是 `/quit`，进程会在取消后立刻退出，jcmd 就来不及取第二次线程，所以要在后面再放一条耗时的输入。`GenerateConsoleCtrlEvent` 要求目标进程在独立 console 里（用 Start-Process，不加 `-NoNewWindow`）。
- 最后一轮 verify 暴露过一个竞态：run 线程先 `countDown`，后把 entry 放进队列，foreground 调用方被唤醒后立刻 flush，有时拿到的是空队列（`the_parent_gets_one_entry…` 偶发失败）。现在改为 `SubagentRun.execute` 的 finally 里先回调 `Env.ended`（入队、notify），再 `countDown`（`SubagentRun.java` execute 的 finally）。修复后用 `flaky.ps1` 把两个测试类连跑 5 轮，5 轮全部通过。
- hooks 链的顺序是 hitl → tasks → verify → subagent（cli pom 的依赖顺序，也是 ServiceLoader 的顺序）。所以审批在拿锁之前，verify 的 afterToolCall 在释放锁之前。live 3 能让两个 edit 必然重叠，靠的就是后者。
