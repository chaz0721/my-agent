## 6. 对规格的偏离与理由

1. **skills 那一句没有加**：skills 索引在 `pai-core/src/main/java/dev/pai/core/skill/SkillsExtension.java` 注入，按 brief 的规则跳过。task (3) 改前已经命中 `load_skill`（tool 描述里本来就写了 "Call it before doing a task the skill covers"），所以没有实际损失。
2. **8.5A 额外改了 hitl 一处（4 行）**：改前 `spawn_agent(explore)` 在 AUTO_READ 下**每次都询问**，提示是 `note: the command is not plain words`。原因是 `ApprovalHooks.readCommand` 把"工具声明为非只读、但本次输入是只读"的调用一律当成 bash 命令检查，而 spawn_agent 没有 `command` 参数，空命令被判为"不是纯词"。这和 8.5A 的目标冲突（改前 live 的第一次尝试里，模型主动派 explore 时被卡在审批上）。**更正（审查）**：原稿说 PLAN 下也受益，不对。PLAN 下 `spawn_agent` 根本不在工具列表里，因为 `PlanMode` 按工具的**声明** effect 过滤，spawn_agent 声明为 EXECUTE。hook 层的测试在 PLAN 下也放行，只是没有实际意义。规格里"PLAN 下可派 explore"目前做不到，要做需要 PlanMode 按输入判断（记为后续）。现在没有 `command` 参数、本次只读、并且 `path` 没有指向 cwd 外的调用，按只读工具处理。子代理自己的每个调用仍然经过 hitl。测试见 `SensitiveFilesTest.a_read_only_call_without_a_command_runs_like_a_read_only_tool`。
3. **规则文本改了两轮**：第一版 live 时 task (1) 没有命中，于是改了 `<sub-agents>` 的措辞（`e72f1c0`），只改提示，任务没有改。三道任务都用终版 jar 重跑了一遍，§1 表格里三列都列出来了。
4. **`{path}` 而不是 `<changed-file>`**：规格里两种写法都允许。另外加了 `{python}` 占位，用来实现 python → python3 回退。项目自己的 `verify.json` 也可以用这两个占位。
5. **`--quiet` 抑制**：cli 零改动，所以没法加新开关。现在 `--quiet` 下 plain renderer 本来就输出到 stderr，进度行和其他工具行一起去 stderr，stdout 上不会出现。规格要的"可被抑制"就是这个效果，但不是靠新增开关实现的。
6. **JLine 的位置**：规格写的是"在状态行下方以一行折叠显示"。实现是放在该 `spawn_agent` 的运行行**下面**（缩进两格，faint），状态行仍然是 live 区最后一行。原因是同时有几个子代理时，每个运行行下面各跟一行，读起来最清楚；如果放在状态行之后，就成了 live 区最底部，会和状态行抢位置。
7. **敏感文件"glob"工具**：pai 里没有内置 glob 工具。实现对所有声明为只读的工具检查 `path` 参数（read，以及将来的 grep/glob 一类），对只读 bash 检查每个词、`=` 后面的值和 `rev:path` 里冒号后面的部分。
8. **主代码 263 行，略超规格的预计（≤ 250）**：多出来的主要是 verify 的 `{python}` 探测与缓存（约 40 行），以及 `{path}` 的路径安全检查。各模块都在预算内。
9. **FileRestorer 还没有读这张表**：它在 cli，并且有自己的正则（`FileRestorer.java:43`）。两边内容现在一致（表文件头注释里写明了这一点）。让它改读 `/dev/pai/core/policy/sensitive-files.txt` 需要改 cli 一行左右，留到下一次允许改 cli 的时候。

## 7. 坑（给后来者）

- **device_commit_files 的 stagedPath 必须唯一**：第一次同步后我改了文件，再用同一个 staged 路径提交，返回 "written"，但电脑上仍是旧内容（测试按旧代码失败）。现在 `scratchpad/stage.sh` 每次都复制到 `/mnt/user-data/outputs/s<纳秒>/…`，提交后用 `hash.ps1` 核对 SHA-256。
- **spotless 是 verify 的一部分**：容器里写的代码要先在电脑上 `spotless:apply`（`fmt.ps1`），再拉回容器（`pull.ps1` 先压平到 `tmp\m85live\pull\`，因为 device_stage_files 只支持 7 层以内的路径），否则容器和电脑的版本会分叉。`unpull.sh` 拷回之后会清空 uploads 目录，否则下一次会把旧文件再拷一遍。
- **预写 stdin 驱动审批不可靠**：命令一带管道就要审批，下一行输入（比如 `/quit`）会被当成审批答案吃掉。要么用 desktop-commander 的交互进程逐条回答（本次的做法，`live.ps1`），要么用 `permissions.json` 预置 allow 规则。allow 规则不匹配含管道或引号的命令（`Permissions` 的设计），所以 `mvn … | tail` 仍然会询问。
- **live 日志的编码**：stdout 被重定向时，JVM 按 GBK 输出，中文和 `—` 会变成 `?`/`��`。`live.ps1` 加了 `-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8`。stdin 本身没有问题（JDK 21 默认 UTF-8）。
- **PAI_DEBUG_HTTP 的输出会全部回到控制台**：交互驱动时每轮请求体都有几 KB，读起来很费上下文。只在一次短任务（skill）上开就够核对 prompt 段了。在 pai-next 仓库本身（有 `.env`）里没有开 HTTP dump。
- `setup-a.ps1` 会删掉同一 phase 的 home 目录。我重跑 todo-after 时误删了 explore-after 的 session 目录，这一轮只剩 `logs\explore-after.log`，表格里的序列就是从这份日志取的。
- **探测 python 用 `--version` 而不是 PATH 查找**：Windows 的 `WindowsApps\python3.exe` 在 PATH 上，但运行就失败（`VerifyRunner.interpreter`）。
- `{path}` 只接受 `[\w.+@/-]+` 形式的路径，而且不能以 `-` 开头（`VerifyRunner.PLAIN_PATH`），因为路径是模型给的，要拼进 shell 命令。审查修复后，不合规的路径（非 ASCII 如 `中文.py`、含空格、含 shell 字符）**只丢弃这一个**，并通过 notify 告诉用户 "verify: not checking …"，其余路径照常检查。全部不合规时不运行，也不向模型回灌失败（原稿写的是"跳过并回灌说明"，已更正）。
- 敏感词匹配的是"词"而不是"文件"：`grep secret src` 里的 `secret` 命中 `*secret*`，也会询问。这是有意偏保守的取舍。symlink 的目标名不检查，只检查写出来的名字（FileRestorer 两者都查）。

## 8. 建议（没有做）

- 把 `ToolExecutionUpdate` 的 partial 做成结构化数据（run id、turn、摘要），去掉 tui 里的正则约定。
- `SkillsExtension` 留一个"索引尾注"的配置点，或者干脆把那一句写进 core 的索引模板（需要授权改 core）。
- `FileRestorer` 改读 `sensitive-files.txt`（cli 一行左右）。
